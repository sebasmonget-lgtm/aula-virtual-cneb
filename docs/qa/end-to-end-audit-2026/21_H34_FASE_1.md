# H34 · Fase 1: cierre sin valoraciones inventadas

Fecha: 28/09/2026. Alcance: aula ficticia QA «Exploradores», 15 niños, frontend 5175 y API 8790. La app personal en 5173/8788 no se tocó. Commit de respaldo previo: `2e7e04e`. No hubo despliegue ni cambios en Project Master o rediseño de interfaz.

## Regla implementada

«Mi año» por sí solo no crea una fila de evaluación en cada bimestre. Entran al alcance del período competencias de actividades completadas, observaciones, valoraciones ya existentes, borradores docentes iniciados o inclusión docente explícita. Un borrador no se puede ocultar retirando la competencia. Un par en alcance puede quedar sin letra como `observation_pending`, `insufficient_information` o `pending` (evidencia por revisar). Una valoración confirmada conserva exclusivamente la letra elegida por la docente; A/B/C requieren conclusión descriptiva y AD la admite como opcional. Borradores incompletos, valoraciones obsoletas y conclusiones obligatorias ausentes bloquean el cierre. P1–P3 pueden cerrarse con pendientes identificados; P4 revisa todo el año y bloquea pares aplicables que nunca recibieron una valoración docente vigente.

Manifiesto de cierre: `entries` solo contiene valoraciones confirmadas; `pending_entries` deja motivo y referencias a evidencia sin nivel. El consolidado, CSV y Excel muestran estado y dejan vacíos nivel/conclusión de los pendientes. Una actividad posterior puede priorizar un pendiente de cierre anterior como nueva oportunidad de observación.

En P1 el CSV devolvió 90 filas: 16 confirmadas, 49 `observation_pending`, 1 `insufficient_information` y 24 `pending`. Ninguna pendiente tenía nivel o conclusión; ninguna confirmada carecía de nivel. Los manifiestos P1–P3 contienen respectivamente 16/74, 5/25 y 5/25 entradas confirmadas/pendientes, sin letra en los pendientes. La ruta de seguimiento de una actividad de P2 devolvió cuatro sugerencias priorizadas con `reason_code=prior_period_pending`. El backend de P4 devolvió HTTP 422 con 163 pares anuales sin valoración vigente. No se añadieron C, otras letras o conclusiones para forzar el cierre; tampoco se retiraron competencias.

El `.xlsx` real de P1 respondió HTTP 200 y su hoja tuvo 91 filas (cabecera más 90 pares), columna «Estado», 49 «Pendiente de observación», 24 «Pendiente de revisión docente» y 1 «Información insuficiente»; la prueba focal verifica celdas de valoración vacías para pendientes.

Después del último ajuste de alcance y estadísticas, la API QA se cerró mediante la ruta de señal del servidor y se reinició correctamente con el mismo directorio restaurado. Una nueva lectura de los cuatro períodos mostró P1–P3 `closed=true/current=true`, P4 `closed=false` y los mismos 163 huecos anuales.

**Resultado de la pregunta de cierre:** P1 y P2 sí se cierran por UI; P3 sí por lógica de servidor, pero no todavía por UI el 28/09 porque termina el 09/10; P4 no debe cerrarse con el estado actual. Por tanto **no está demostrado ni permitido cerrar P1–P4 completos** sin nuevas evidencias y decisiones docentes. La restricción de fecha de la UI es separada de H34 y no se anuló.

## Integridad del entorno de prueba

Al reiniciar la API QA, el directorio PGlite anterior y una copia hecha después del apagado reportaron checkpoint inválido. Se preservaron y no se abrió la base original de la usuaria. La prueba se repitió en un directorio QA nuevo restaurado desde `evidencias/p4-audit-final-qa-snapshot.json`, el último export de la auditoría. No es una copia byte a byte: el export omite algunas tablas; dos actividades semilla recibieron timestamps nuevos al reinstalar. Sí se conciliaron por JSON idéntico las 24 actividades QA, las 138 evidencias, las 68 versiones de valoración y las 32 conclusiones. La restauración no reescribió esos registros pedagógicos; solo se añadieron los tres cierres QA de esta prueba.
